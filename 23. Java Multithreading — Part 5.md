## 2. Lock-Free Mechanism — CAS (Compare-and-Swap)

- Uses the **CAS (Compare and Swap)** technique.
- It's a **low-level CPU operation** — hardware-supported.
- It's **atomic** — happens as a single, indivisible instruction.
- **All modern processors** support it.

### 3 Parameters of CAS:

|Parameter|Description|
|---|---|
|**Memory Location**|Location where the variable is stored|
|**Expected Value**|Value which should currently be present at that memory location|
|**New Value**|Value to write IF the current value matches the expected value|

### How CAS works:

```
CAS(memoryLocation, expectedValue, newValue):
  if (memoryLocation.value == expectedValue):
      memoryLocation.value = newValue   ← success, swap done
      return true
  else:
      return false  ← someone else changed it first, retry
```

### ABA Problem:

- CAS checks if value is still the **expected value**, but what if another thread changed A→B→A?
- The value looks the same but it was actually modified in between.
- **Solved using version number or timestamp** (e.g., `AtomicStampedReference`).

## 3. What ATOMIC means?

- **Atomic = Single / "All or nothing"**
- An atomic operation either completes fully or doesn't happen at all — no partial state visible to other threads.

### The Problem — Race Condition with plain `int`:

```java
// Single-threaded — works fine
public class SharedResource {
    int counter;

    public void increment() {
        counter++;   // NOT atomic: read → increment → write (3 steps!)
    }

    public int get() {
        return counter;
    }
}

public class Main {
    public static void main(String[] args) {
        SharedResource resource = new SharedResource();
        for (int i = 0; i < 400; i++) {
            resource.increment();
        }
        System.out.println(resource.get());
        // Output: 400  ✅ (single thread is fine)
    }
}
```

```java
// Multi-threaded — RACE CONDITION! counter++ is NOT atomic
public class Main {
    public static void main(String[] args) {
        SharedResource resource = new SharedResource();

        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 200; i++) resource.increment();
        });
        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 200; i++) resource.increment();
        });

        t1.start();
        t2.start();

        try {
            t1.join();
            t2.join();
        } catch (Exception e) {}

        System.out.println(resource.get());
        // Output: 371 (not 400!) — race condition corrupts the count ❌
    }
}
```

> `counter++` is **NOT atomic** — it's 3 operations: read → increment → write. Two threads can both read the same value and both write back the same incremented value, losing one increment.

## 4. Two Solutions for Race Condition on Counter

### Solution 1 — Lock-based: `synchronized`

```java
public class SharedResource {
    int counter;

    public synchronized void increment() {
        counter++;   // only 1 thread at a time
    }

    public int get() {
        return counter;
    }
}
// Output: always 400 ✅ — but has lock overhead
```

### Solution 2 — Lock-free: `AtomicInteger`

```java
public class SharedResource {
    AtomicInteger counter = new AtomicInteger(initialValue: 0);

    public void increment() {
        counter.incrementAndGet();   // CAS-based atomic increment — no lock needed!
    }

    public int get() {
        return counter.get();
    }
}
// Output: always 400 ✅ — no locks, better performance under contention
```

### synchronized vs AtomicInteger:

||`synchronized`|`AtomicInteger`|
|---|---|---|
|Mechanism|Lock-based|Lock-free (CAS)|
|Thread blocking|Yes — other threads blocked|No — spin retry|
|Performance (low contention)|Similar|Similar|
|Performance (high contention)|Worse (lock contention)|Better|
|Use case|Complex multi-step operations|Single variable counter/flag|

## 5. Atomic Classes — Full Reference

All in `java.util.concurrent.atomic` package.

### `AtomicInteger`

```java
AtomicInteger ai = new AtomicInteger(0);

ai.get()                    // get current value
ai.set(5)                   // set value
ai.getAndIncrement()        // return then increment (i++)
ai.incrementAndGet()        // increment then return (++i)
ai.getAndDecrement()        // return then decrement
ai.decrementAndGet()        // decrement then return
ai.addAndGet(5)             // add 5 and return result
ai.getAndAdd(5)             // return current then add 5
ai.compareAndSet(expected, newVal)  // CAS — set if current == expected
```

### `AtomicBoolean`

```java
AtomicBoolean ab = new AtomicBoolean(false);

ab.get()                          // get current value
ab.set(true)                      // set value
ab.getAndSet(true)                // return old, set new
ab.compareAndSet(false, true)     // CAS — set to true only if currently false
```

### `AtomicLong`

```java
AtomicLong al = new AtomicLong(0L);
// same methods as AtomicInteger but for long
al.incrementAndGet();
al.addAndGet(100L);
al.compareAndSet(expected, newVal);
```

### `AtomicReference<T>`

```java
// For atomically updating object references
AtomicReference<String> ref = new AtomicReference<>("hello");

ref.get()                          // get current reference
ref.set("world")                   // set reference
ref.compareAndSet("hello", "world") // CAS on object reference
ref.getAndSet("newVal")            // return old ref, set new
```

### `AtomicStampedReference<T>` — Solves ABA Problem

```java
// Pairs value with a version stamp to detect ABA
AtomicStampedReference<Integer> asr = new AtomicStampedReference<>(10, 0);

int[] stampHolder = new int[1];
Integer value = asr.get(stampHolder);  // get value and stamp
int currentStamp = stampHolder[0];

// CAS with stamp check — won't succeed if stamp changed even if value reverted
asr.compareAndSet(10, 20, currentStamp, currentStamp + 1);
```

## 6. Concurrent Collections

Standard Java collections (`ArrayList`, `HashMap`, etc.) are **NOT thread-safe**. Use Concurrent Collections for thread-safe alternatives.

### Collection Hierarchy (key thread-safe classes highlighted):

```
Iterable
  └── Collection
        ├── Queue
        │     ├── PriorityQueue  → PriorityBlockingQueue (ReentrantLock)
        │     └── Deque
        │           ├── ArrayDeque  → ConcurrentLinkedDeque (CAS)
        │           └── LinkedList  → ConcurrentLinkedDeque (CAS)
        ├── List
        │     ├── ArrayList    → CopyOnWriteArrayList (ReentrantLock)
        │     ├── Vector       (synchronized — legacy)
        │     └── LinkedList
        └── Set
              ├── HashSet      → newKeySet() inside ConcurrentHashMap (Synchronized)
              ├── LinkedHashSet → Collections.synchronizedSet (Synchronized)
              ├── TreeSet      → Collections.synchronizedSortedSet (Synchronized)
              └── NavigableSet

Map (separate hierarchy)
  ├── HashMap      → ConcurrentHashMap (Segment locking / CAS)
  ├── HashTable    (synchronized — legacy)
  ├── LinkedHashMap
  └── SortedMap
        └── TreeMap
```

### Concurrent Collection — Quick Reference Table:

|Collection|Concurrent Collection|Lock Mechanism|
|---|---|---|
|`PriorityQueue`|`PriorityBlockingQueue`|ReentrantLock|
|`LinkedList`|`ConcurrentLinkedDeque`|Compare-and-swap (CAS)|
|`ArrayDeque`|`ConcurrentLinkedDeque`|Compare-and-swap (CAS)|
|`ArrayList`|`CopyOnWriteArrayList`|ReentrantLock|
|`HashSet`|`newKeySet()` in `ConcurrentHashMap`|Synchronized|
|`TreeSet`|`Collections.synchronizedSortedSet`|Synchronized|
|`LinkedHashSet`|`Collections.synchronizedSet`|Synchronized|
|Queue Interface|`ConcurrentLinkedQueue`|Compare-and-swap (CAS)|
|`HashMap`|`ConcurrentHashMap`|CAS + segment locking|

## 7. Key Concurrent Collection Details

### `ConcurrentHashMap`

- Divides the map into **segments** (buckets) — different threads can operate on different segments simultaneously.
- Uses **CAS** for some operations, segment-level locking for others.
- `null` keys and values are **NOT** allowed (unlike `HashMap`).
- Much better than `Hashtable` (which synchronizes the entire map).

```java
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();
map.put("a", 1);
map.get("a");
map.putIfAbsent("b", 2);           // atomic — only puts if key absent
map.computeIfAbsent("c", k -> 3);  // atomic compute
```

### `CopyOnWriteArrayList`

- On every **write** (add, set, remove), creates a **new copy** of the underlying array.
- Reads are lock-free — no synchronization needed.
- Best for **read-heavy, write-rare** scenarios (e.g., listener lists).

```java
CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>();
list.add("a");   // creates new internal array copy
list.get(0);     // lock-free read
```

### `PriorityBlockingQueue`

- Thread-safe priority queue.
- **Blocks** on `take()` when empty — great for producer-consumer.

```java
PriorityBlockingQueue<Integer> pbq = new PriorityBlockingQueue<>();
pbq.put(5);
pbq.put(1);
pbq.take();  // blocks if empty; returns 1 (smallest)
```

### `ConcurrentLinkedQueue`

- Lock-free, thread-safe FIFO queue using CAS.
- Non-blocking — `poll()` returns `null` if empty (doesn't block).

```java
ConcurrentLinkedQueue<String> clq = new ConcurrentLinkedQueue<>();
clq.offer("task1");
String task = clq.poll();  // returns null if empty
```

## 8. Common Interview Questions

**Q1. What is CAS (Compare-and-Swap)?**

> CAS is a low-level atomic CPU operation with three parameters: memory location, expected value, and new value. It atomically checks if the memory location holds the expected value and, only if it does, swaps in the new value. It's the foundation of all lock-free data structures in Java.

**Q2. What is the ABA problem in CAS? How is it solved?**

> The ABA problem occurs when a value changes from A → B → A. CAS sees the value is still A and proceeds, unaware that it was modified. Solved using `AtomicStampedReference` which pairs the value with a version number (stamp) — even if the value reverts, the stamp changes, so CAS detects the modification.

**Q3. Why is `counter++` not atomic in Java?**

> `counter++` compiles to three bytecode instructions: read the value, increment it, write it back. Two threads can interleave these steps — both can read the same value and both write back the same result, causing one increment to be lost (race condition).

**Q4. What is the difference between `AtomicInteger` and `synchronized`?**

> Both fix race conditions. `synchronized` uses a lock — one thread blocks all others. `AtomicInteger` uses CAS (lock-free) — threads retry on conflict instead of blocking. `AtomicInteger` is more efficient under high contention for simple single-variable operations.

**Q5. What is `ConcurrentHashMap`? How is it different from `Hashtable`?**

> Both are thread-safe Maps. `Hashtable` synchronizes every method on the entire map object — only one thread can access it at a time. `ConcurrentHashMap` uses segment-level locking and CAS, allowing multiple threads to operate on different segments simultaneously — much higher throughput. Also: `Hashtable` allows null keys/values; `ConcurrentHashMap` does not.

**Q6. What is `CopyOnWriteArrayList`? When should you use it?**

> It creates a fresh copy of the underlying array on every write operation. Reads are completely lock-free. Use it when reads vastly outnumber writes (e.g., event listener lists, observer lists). Avoid it for write-heavy workloads — the array copy on every write is expensive.

**Q7. What is the difference between `ConcurrentLinkedQueue` and `PriorityBlockingQueue`?**

> `ConcurrentLinkedQueue` is lock-free (CAS-based) and non-blocking — `poll()` returns `null` when empty. `PriorityBlockingQueue` uses `ReentrantLock` and **blocks** on `take()` when empty — useful for producer-consumer patterns where consumers should wait for work.

**Q8. What are Atomic classes in Java? Name them.**

> Atomic classes in `java.util.concurrent.atomic` provide lock-free thread-safe operations on single variables using CAS. Key classes: `AtomicInteger`, `AtomicLong`, `AtomicBoolean`, `AtomicReference<T>`, `AtomicStampedReference<T>` (solves ABA), `AtomicIntegerArray`, `AtomicLongArray`.
