
## Problem Summary

Build a Java program that reads multiple text files concurrently. Each line or data entry should be processed and printed with the name of the thread that handled it. The solution should use Java's `ExecutorService` to manage worker threads and shut them down gracefully after all file-reading tasks finish.

Core expectation:

```text
pool-1-thread-1 processed sample_logs_1.txt: first line
pool-1-thread-2 processed sample_logs_2.txt: another line
pool-1-thread-1 processed sample_logs_3.txt: final line
```

## Why Not Manually Create Threads?

Manual thread creation means doing something like this:

```java
Thread t1 = new Thread(() -> readFile("file1.txt"));
Thread t2 = new Thread(() -> readFile("file2.txt"));

t1.start();
t2.start();

t1.join();
t2.join();
```

This works for a tiny example, but it does not scale well.

### Problems With Manual Threads

- **Manual lifecycle management:** You must create, start, join, interrupt, and clean up threads yourself.
- **Poor separation of concerns:** Business logic and thread-management logic get mixed together.
- **Resource exhaustion:** Creating one thread per file can overwhelm the system if there are hundreds or thousands of files.
- **Thread creation overhead:** Creating threads repeatedly is expensive compared to reusing existing worker threads.
- **Harder error handling:** Collecting failures from multiple threads becomes awkward.
- **No built-in task queue:** If all workers are busy, you must manually decide where pending work waits.

## Executor Framework

The Executor framework is part of `java.util.concurrent`. It separates task submission from thread management.

Instead of creating threads directly, we submit tasks to an executor. The executor decides when and on which worker thread each task runs.

### Restaurant Kitchen Analogy

Think of tasks as food orders and worker threads as chefs.

Without a thread pool, the restaurant hires a new chef for every order. That is wasteful.

With a thread pool, the restaurant has a fixed number of chefs. Orders wait in a queue, and available chefs pick them up one by one.

## Core Components

### `Executor`

The base interface.

```java
void execute(Runnable command);
```

It only knows how to execute a `Runnable`. It does not provide lifecycle methods like shutdown.

### `ExecutorService`

A richer interface that extends `Executor`.

Important methods:

```java
execute(Runnable task)
submit(Runnable task)
submit(Callable<T> task)
shutdown()
shutdownNow()
awaitTermination(timeout, unit)
```

Use `ExecutorService` in most real applications because it supports task submission, result tracking, and controlled shutdown.

### `ThreadPoolExecutor`

The main concrete implementation behind many executor factory methods.

It manages:

- Core pool size
- Maximum pool size
- Task queue
- Thread keep-alive time
- Rejection policy

### `Executors`

A utility factory class used to create common executor types.

Examples:

```java
Executors.newFixedThreadPool(2);
Executors.newSingleThreadExecutor();
Executors.newCachedThreadPool();
Executors.newScheduledThreadPool(2);
```

## Thread Pool Lifecycle

1. **Submit:** Tasks are submitted using `execute()` or `submit()`.
2. **Queue:** If all worker threads are busy, tasks wait in a queue.
3. **Execute:** Worker threads pick tasks from the queue and run them.
4. **Shutdown:** The executor stops accepting new tasks and eventually terminates after submitted tasks finish.

## `execute()` vs `submit()`

### `execute(Runnable)`

- Takes only a `Runnable`.
- Returns `void`.
- Exceptions are typically handled by the thread's uncaught exception handler.
- Good for fire-and-forget tasks.

```java
executor.execute(() -> readFile(filePath));
```

### `submit(...)`

- Accepts `Runnable` or `Callable`.
- Returns a `Future`.
- Exceptions are captured inside the `Future` and rethrown when calling `future.get()`.
- Good when you need results or error tracking.

```java
Future<Integer> future = executor.submit(() -> countLines(filePath));
Integer lineCount = future.get();
```

## `Runnable` vs `Callable`

### `Runnable`

- Does not return a value.
- Cannot throw checked exceptions directly from `run()`.

```java
Runnable task = () -> readFile("sample.txt");
```

### `Callable<T>`

- Returns a value.
- Can throw checked exceptions.

```java
Callable<Integer> task = () -> countLines("sample.txt");
```

Use `Callable` when the interviewer asks for results, error propagation, or file statistics.

## Concurrent File Reader Example

This version reads multiple files using a fixed thread pool and shuts down gracefully.

```java
import java.io.BufferedReader;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class ConcurrentFileReader {

    public static void main(String[] args) {
        List<Path> filePaths = List.of(
            Path.of("sample_logs_1.txt"),
            Path.of("sample_logs_2.txt"),
            Path.of("sample_logs_3.txt")
        );

        int poolSize = 2;
        ExecutorService executorService = Executors.newFixedThreadPool(poolSize);

        for (Path filePath : filePaths) {
            executorService.execute(() -> readFile(filePath));
        }

        shutdownGracefully(executorService);
    }

    private static void readFile(Path filePath) {
        String threadName = Thread.currentThread().getName();

        try (BufferedReader reader = Files.newBufferedReader(filePath)) {
            String line;

            while ((line = reader.readLine()) != null) {
                System.out.println(threadName + " processed " + filePath + ": " + line);
            }
        } catch (IOException e) {
            System.err.println(threadName + " failed to read " + filePath + ": " + e.getMessage());
        }
    }

    private static void shutdownGracefully(ExecutorService executorService) {
        executorService.shutdown();

        try {
            if (!executorService.awaitTermination(30, TimeUnit.SECONDS)) {
                executorService.shutdownNow();
            }
        } catch (InterruptedException e) {
            executorService.shutdownNow();
            Thread.currentThread().interrupt();
        }
    }
}
```

## Why Use `shutdown()`?

After submitting all tasks, call:

```java
executorService.shutdown();
```

This means:

- No new tasks will be accepted.
- Already submitted tasks continue running.
- The executor terminates once all submitted tasks complete.

Without shutdown, the JVM may keep running because executor worker threads are still alive.

## `shutdown()` vs `shutdownNow()`

### `shutdown()`

- Graceful shutdown.
- Stops accepting new tasks.
- Lets queued and running tasks finish.

### `shutdownNow()`

- Attempts immediate shutdown.
- Tries to interrupt running tasks.
- Returns tasks that were submitted but never started.

Interview answer:

> Use `shutdown()` for normal completion. Use `shutdownNow()` only as a fallback when tasks do not finish within a timeout or when the application needs urgent cancellation.

## Why Use `awaitTermination()`?

`shutdown()` starts the shutdown process but does not block the current thread until completion.

Use `awaitTermination()` when the main thread needs to wait for worker tasks to finish.

```java
executorService.shutdown();
executorService.awaitTermination(30, TimeUnit.SECONDS);
```

## Choosing Pool Size

For file reading, tasks are usually I/O-bound, not CPU-bound.

General guidelines:

- **CPU-bound work:** Pool size close to number of CPU cores.
- **I/O-bound work:** Pool size can be larger than CPU cores because threads spend time waiting on disk or network I/O.
- **Small demo:** A fixed pool of `2` threads is enough to show queuing and reuse.

Example:

```java
ExecutorService executor = Executors.newFixedThreadPool(2);
```

With 3 files and 2 threads:

- Two files may start immediately.
- The third waits in the queue.
- When one worker finishes, it picks up the third file.

## Expected Execution Behavior

The output order is not deterministic.

That is normal in concurrent programs. Different files may be processed in different orders depending on thread scheduling, file size, disk speed, and OS behavior.

Example:

```text
pool-1-thread-1 processed sample_logs_1.txt: A
pool-1-thread-2 processed sample_logs_2.txt: X
pool-1-thread-1 processed sample_logs_1.txt: B
pool-1-thread-2 processed sample_logs_2.txt: Y
pool-1-thread-1 processed sample_logs_3.txt: M
```

## Common Interview Follow-Ups

### What is a thread pool?

A thread pool is a group of reusable worker threads. Instead of creating a new thread for every task, tasks are submitted to a queue and existing worker threads execute them.

### Why is a thread pool better than creating threads manually?

It reduces thread-creation overhead, avoids uncontrolled resource usage, provides task queuing, improves scalability, and separates business logic from thread management.

### What happens if all threads are busy?

The submitted task waits in the executor's work queue until a worker thread becomes available.

### Is file reading thread-safe here?

Yes, because each task reads a separate file using its own local `BufferedReader`. There is no shared mutable file-reader state.

The console output may interleave, but each individual `println` call is synchronized internally by `PrintStream`.

### Can two threads read the same file?

Yes, multiple threads can read the same file independently if each thread creates its own reader. However, it may be inefficient and output ordering will be nondeterministic.

### How do you collect results from each file?

Use `Callable<T>` and `Future<T>`.

Example:

```java
Future<Integer> future = executor.submit(() -> countLines(filePath));
int count = future.get();
```

### How do you handle exceptions from worker tasks?

Options:

- Catch exceptions inside the task.
- Use `submit()` and inspect exceptions with `Future.get()`.
- Configure a custom `ThreadFactory` with an uncaught exception handler.

With `submit()`, exceptions are wrapped in `ExecutionException`.

### Why might `Executors.newFixedThreadPool()` be risky in production?

`newFixedThreadPool()` uses an unbounded queue. If tasks are submitted faster than they complete, memory usage can grow too much.

For production systems with strict limits, consider creating a `ThreadPoolExecutor` manually with a bounded queue and a rejection policy.

## Production-Style Thread Pool Example

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2,
    4,
    60,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

This gives more control over queue size and overload behavior.

## Key Terms to Remember

- **Task:** A unit of work, usually a `Runnable` or `Callable`.
- **Worker thread:** A thread inside the pool that executes tasks.
- **Work queue:** Where tasks wait when all worker threads are busy.
- **Future:** A handle used to retrieve a task result or exception.
- **Graceful shutdown:** Stop accepting new tasks while allowing existing tasks to complete.
- **Thread reuse:** Existing worker threads execute multiple tasks over time.

## Strong Interview Answer

For this problem, I would use `ExecutorService` with a fixed thread pool. Each file-reading operation becomes a separate `Runnable` task. The executor manages worker threads and queues tasks if all workers are busy. Each task reads its file using a local `BufferedReader` and prints each line with `Thread.currentThread().getName()`. After submitting all tasks, I call `shutdown()` to stop accepting new work and use `awaitTermination()` to wait for completion. This is better than manually creating threads because it reuses threads, reduces overhead, avoids uncontrolled thread growth, and separates concurrency management from file-processing logic.
