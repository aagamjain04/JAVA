

## POJO (Plain Old Java Object)

A POJO is a simple Java class with:

- Public class declaration
- Default public constructor
- Private variables
- Getter and Setter methods

**Example Structure**:

```java
public class User {
    private String name;
    private int age;
    
    public User() {
        // Default constructor
    }
    
    public String getName() {
        return name;
    }
    
    public void setName(String name) {
        this.name = name;
    }
    
    public int getAge() {
        return age;
    }
    
    public void setAge(int age) {
        this.age = age;
    }
}
```

**Best Practice**: When a component receives data/requests, map the request object to a POJO that all other classes understand and use. This centralization means if anything changes in the future, you only need to modify the POJO.

## ENUM CLASS

### Normal Enum Class

**Internal Value Assignment**:

- Each constant in an enum is internally assigned a value starting from 0
- MONDAY = 0, TUESDAY = 1, and so on (if custom values aren't defined)
- This assigned value is called an **ordinal**

**Example**:

```java
public enum Day {
    MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY, SATURDAY, SUNDAY
}
```

**Key Methods**:

- `EnumSample.values()` - Returns an array of all constants in the enum
- `EnumValue.valueOf("FRIDAY")` - Iterates over all constants and returns the one matching the given string exactly
- `name()` - Returns the name of the constant

**Usage Example**:

```java
// Get all values
Day[] days = Day.values();

// Get specific constant
Day day = Day.valueOf("FRIDAY");

// Get name
String name = day.name(); // Returns "FRIDAY"
```

### Enum with Custom Values

- Each variable defined in an enum class applies to every constant
- Each constant is essentially an object of the enum class with the defined variables
- Requires a parameterized constructor that's invoked for every constant
- **Static methods** apply to the whole enum class
- **Non-static methods** are applicable to individual constants

**Example**:

```java
public enum Day {
    MONDAY("Mon", 1),
    TUESDAY("Tue", 2),
    WEDNESDAY("Wed", 3),
    THURSDAY("Thu", 4),
    FRIDAY("Fri", 5),
    SATURDAY("Sat", 6),
    SUNDAY("Sun", 7);
    
    private String shortForm;
    private int dayNumber;
    
    // Parameterized constructor - invoked for each constant
    Day(String shortForm, int dayNumber) {
        this.shortForm = shortForm;
        this.dayNumber = dayNumber;
    }
    
    public String getShortForm() {
        return shortForm;
    }
    
    public int getDayNumber() {
        return dayNumber;
    }
    
    // Static method - for the whole enum class
    public static Day getByNumber(int num) {
        for (Day day : values()) {
            if (day.dayNumber == num) {
                return day;
            }
        }
        return null;
    }
    
    // Non-static method - applicable to all constants
    public void displayInfo() {
        System.out.println(this.name() + " - " + this.shortForm);
    }
}
```

### Method Override by Constant

Since non-static methods are applicable to all constants, you can override a method for a particular constant to get different behavior.

**Example**:

```java
public enum Day {
    MONDAY {
        @Override
        public void dummyMethod() {
            System.out.println("Overridden for MONDAY");
        }
    },
    TUESDAY,
    WEDNESDAY,
    THURSDAY,
    FRIDAY,
    SATURDAY,
    SUNDAY;
    
    // Non-static method
    public void dummyMethod() {
        System.out.println("Default implementation");
    }
}

// Usage
Day.MONDAY.dummyMethod();    // Output: Overridden for MONDAY
Day.TUESDAY.dummyMethod();   // Output: Default implementation
```

### Enum with Abstract Method

Enums can have abstract methods that must be implemented by all constants.

**Example**:

```java
public enum Operation {
    ADD {
        @Override
        public int apply(int a, int b) {
            return a + b;
        }
    },
    SUBTRACT {
        @Override
        public int apply(int a, int b) {
            return a - b;
        }
    },
    MULTIPLY {
        @Override
        public int apply(int a, int b) {
            return a * b;
        }
    },
    DIVIDE {
        @Override
        public int apply(int a, int b) {
            return a / b;
        }
    };
    
    // Abstract method - must be implemented by all constants
    public abstract int apply(int a, int b);
}

// Usage
int result = Operation.ADD.apply(5, 3); // Returns 8
```

### Enum Implements Interface

Enums can implement interfaces, allowing you to call interface methods on every constant.

**Example**:

```java
interface Convertible {
    String toLowerCase();
}

public enum Day implements Convertible {
    MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY, SATURDAY, SUNDAY;
    
    @Override
    public String toLowerCase() {
        return this.name().toLowerCase();
    }
}

// Usage
String day = Day.MONDAY.toLowerCase(); // Returns "monday"
```

### Advantages of Enum over Static Final Constants

**Comparison Example**:

**Using Static Final (Old Way)**:

```java
public class Constants {
    public static final int MONDAY = 1;
    public static final int TUESDAY = 2;
    public static final int WEDNESDAY = 3;
}

// Problem: No type safety
public void processDay(int day) {
    // Can pass any integer, even invalid ones like 99
}

processDay(99); // Compiles fine but logically wrong
```

**Using Enum (Better Way)**:

```java
public enum Day {
    MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY, SATURDAY, SUNDAY
}

// Type safety enforced
public void processDay(Day day) {
    // Can only pass valid Day constants
}

processDay(Day.MONDAY); // Correct
processDay(99);         // Compilation error
```

**Advantages**:

1. **Better Readability**: Code is more expressive and self-documenting
2. **Type Safety**: Compiler enforces that only valid enum values can be passed
3. **Control**: You have complete control over what values can be used

## FINAL CLASS

A class that **cannot be inherited** (extended by other classes).

**Example**:

```java
public final class DatabaseConfig {
    private String url;
    private String username;
    
    public DatabaseConfig(String url, String username) {
        this.url = url;
        this.username = username;
    }
    
    // Methods...
}

// This will give compilation error
// class ExtendedConfig extends DatabaseConfig { } // ERROR!
```

## SINGLETON CLASS

**Objective**: Create only a single object of the class (e.g., for database connections)

### Ways to Create Singleton Classes

1. Eager Initialization
2. Lazy Initialization
3. Synchronization Block
4. Double Check Lock
5. Bill Pugh Solution
6. Enum Singleton

### 1. Eager Initialization

**Implementation**:

1. Create and initialize the object as `private static` (associated with class, not accessible outside)
2. Create `private constructor` to prevent object creation using `new` keyword
3. Provide a `public static method` that returns the single instance

**Code Example**:

```java
public class DatabaseConnection {
    // Step 1: Create and initialize the object as private static
    private static DatabaseConnection instance = new DatabaseConnection();
    
    // Step 2: Private constructor to prevent instantiation
    private DatabaseConnection() {
        System.out.println("Database Connection Created");
    }
    
    // Step 3: Public static method to get the instance
    public static DatabaseConnection getInstance() {
        return instance;
    }
    
    public void connect() {
        System.out.println("Connected to database");
    }
}

// Usage
DatabaseConnection db1 = DatabaseConnection.getInstance();
DatabaseConnection db2 = DatabaseConnection.getInstance();
// db1 and db2 refer to the same object
```

**Disadvantage**: Object is created and initialized at program startup, even if not currently needed by others. This wastes resources if the singleton is never used.

### 2. Lazy Initialization

**Improvement**: Object is created only when someone calls the provided method for the first time. After that, the same object is returned for all subsequent calls.

**Code Example**:

```java
public class DatabaseConnection {
    // Object not initialized yet
    private static DatabaseConnection instance;
    
    private DatabaseConnection() {
        System.out.println("Database Connection Created");
    }
    
    public static DatabaseConnection getInstance() {
        // Create object only when first requested
        if (instance == null) {
            instance = new DatabaseConnection();
        }
        return instance;
    }
    
    public void connect() {
        System.out.println("Connected to database");
    }
}
```

**Disadvantage**: If two threads try to get the object simultaneously and it's null, both will pass the `if (instance == null)`check, and two objects will be created (thread-safety issue).

**Scenario**:

```
Thread-1: Checks instance == null (true)
Thread-2: Checks instance == null (true)
Thread-1: Creates new instance
Thread-2: Creates new instance
Result: Two objects created!
```

### 3. Synchronized Method

**Solution**: Uses `synchronized` keyword to overcome the lazy initialization problem.

**How it works**:

- Puts a lock on the method
- Only one thread can enter the method at a time
- Prevents possibility of creating 2 objects

**Code Example**:

```java
public class DatabaseConnection {
    private static DatabaseConnection instance;
    
    private DatabaseConnection() {
        System.out.println("Database Connection Created");
    }
    
    // Synchronized method - only one thread at a time
    public static synchronized DatabaseConnection getInstance() {
        if (instance == null) {
            instance = new DatabaseConnection();
        }
        return instance;
    }
    
    public void connect() {
        System.out.println("Connected to database");
    }
}
```

**Disadvantage**: Very slow due to synchronization overhead. Every call to `getInstance()` must acquire and release a lock, even after the instance is created. Generally not used in practice.

### 4. Double Checked Locking (Most Commonly Used)

**Improvement**: Overcomes the slowness of synchronized method by applying `synchronized` to a block instead of the entire method. Lock/unlock happens only once during object creation.

**Code Example**:

```java
public class DatabaseConnection {
    private static DatabaseConnection instance;
    
    private DatabaseConnection() {
        System.out.println("Database Connection Created");
    }
    
    public static DatabaseConnection getInstance() {
        // First check without synchronization (fast)
        if (instance == null) {
            // Synchronized block only when instance is null
            synchronized (DatabaseConnection.class) {
                // Second check inside synchronized block
                if (instance == null) {
                    instance = new DatabaseConnection();
                }
            }
        }
        return instance;
    }
    
    public void connect() {
        System.out.println("Connected to database");
    }
}
```

**Memory Issue Problem**:

```
Core-1          Core-2
L1 Cache        L1 Cache
    \            /
      Memory
```

Each core has dedicated L1 Cache that periodically syncs with memory.

**Scenario**:

- Thread T1 (on Core-1) enters method, gets null, creates object in **cache**
- Thread T2 (on Core-2) tries to get object before T1's object syncs to **memory**
- T2 sees null in memory and creates a second object
- Result: Two objects created despite double-checked locking

**Solution**: Use `volatile` keyword

```java
public class DatabaseConnection {
    // volatile ensures object is created in memory, not cache
    private static volatile DatabaseConnection instance;
    
    private DatabaseConnection() {
        System.out.println("Database Connection Created");
    }
    
    public static DatabaseConnection getInstance() {
        if (instance == null) {
            synchronized (DatabaseConnection.class) {
                if (instance == null) {
                    instance = new DatabaseConnection();
                }
            }
        }
        return instance;
    }
    
    public void connect() {
        System.out.println("Connected to database");
    }
}
```

`volatile` ensures:

- Object is created directly in memory (not cache)
- All read/write operations happen in memory
- Prevents the caching issue

**Disadvantage**: Slightly slower due to memory synchronization, but much faster than full method synchronization.

### 5. Bill Pugh Solution

Solves eager initialization issue by placing the object inside a **private static nested class**.

**Why it works**: The nested class doesn't get loaded at program startup; it's only loaded when referenced (when `getInstance()` is called for the first time).

**Code Example**:

```java
public class DatabaseConnection {
    
    private DatabaseConnection() {
        System.out.println("Database Connection Created");
    }
    
    // Private static nested class
    // This class is loaded only when referenced
    private static class SingletonHelper {
        private static final DatabaseConnection INSTANCE = new DatabaseConnection();
    }
    
    public static DatabaseConnection getInstance() {
        // SingletonHelper is loaded here for the first time
        return SingletonHelper.INSTANCE;
    }
    
    public void connect() {
        System.out.println("Connected to database");
    }
}
```

**Advantages**:

- Lazy initialization (object created only when needed)
- Thread-safe (class loading is thread-safe by JVM)
- No synchronization overhead
- Best practice for most use cases

### 6. Enum Singleton

**Key Properties**:

- All enum constructors are private by default
- Only one object of each enum constant is created per JVM
- By default, enums are singleton
- Thread-safe by design

**Code Example**:

```java
public enum DatabaseConnection {
    INSTANCE; // The singleton instance
    
    // Constructor is private by default
    DatabaseConnection() {
        System.out.println("Database Connection Created");
    }
    
    public void connect() {
        System.out.println("Connected to database");
    }
}

// Usage
DatabaseConnection.INSTANCE.connect();
```

**Advantages**:

- Simplest and most effective singleton implementation
- Inherently thread-safe
- Prevents reflection attacks (normal singletons can be broken via reflection)
- Serialization-safe
- Joshua Bloch (author of "Effective Java") recommends this approach

## IMMUTABLE CLASSES

To create truly immutable classes, you need to ensure that the internal state cannot be modified after object creation.

**Key Principles**:

1. Make the class `final` (cannot be extended)
2. Make all fields `private` and `final`
3. Don't provide setter methods
4. If fields are mutable objects (like collections), return copies instead of original references

**Example**:

```java
import java.util.ArrayList;
import java.util.List;

public final class ImmutablePerson {
    private final String name;
    private final int age;
    private final List<String> hobbies;
    
    public ImmutablePerson(String name, int age, List<String> hobbies) {
        this.name = name;
        this.age = age;
        // Create a defensive copy of the list
        this.hobbies = new ArrayList<>(hobbies);
    }
    
    public String getName() {
        return name;
    }
    
    public int getAge() {
        return age;
    }
    
    // Return a copy of the list, not the original
    public List<String> getHobbies() {
        return new ArrayList<>(this.hobbies);
    }
}

// Usage
List<String> hobbies = new ArrayList<>();
hobbies.add("Reading");
hobbies.add("Gaming");

ImmutablePerson person = new ImmutablePerson("John", 25, hobbies);

// This won't affect the person's hobbies
List<String> retrievedHobbies = person.getHobbies();
retrievedHobbies.add("Swimming");

// person's hobbies remain unchanged
System.out.println(person.getHobbies()); // [Reading, Gaming]
```

**Why Return Copies?**

Without returning a copy:

```java
// BAD - Mutable reference returned
public List<String> getHobbies() {
    return this.hobbies; // Returns actual reference
}

// User can modify the internal state!
person.getHobbies().add("New Hobby"); // Modifies internal list!
```

With copy:

```java
// GOOD - Copy returned
public List<String> getHobbies() {
    return new ArrayList<>(this.hobbies); // Returns copy
}

// User modifications don't affect the original
person.getHobbies().add("New Hobby"); // Only modifies the copy
```

Since we're passing the copy of the list, new items won't be added to the original, making it truly immutable.

## WRAPPER CLASS

Wrapper classes convert primitive types to objects. They provide:

- Object representation of primitives
- Utility methods for conversion
- Ability to use primitives in collections (which require objects)

**Primitive to Wrapper Mapping**:

```
byte    -> Byte
short   -> Short
int     -> Integer
long    -> Long
float   -> Float
double  -> Double
char    -> Character
boolean -> Boolean
```

**Example**:

```java
// Autoboxing - primitive to wrapper
Integer num = 10; // int to Integer

// Unboxing - wrapper to primitive
int value = num; // Integer to int

// Useful in collections
List<Integer> numbers = new ArrayList<>();
numbers.add(5); // Autoboxing
int first = numbers.get(0); // Unboxing

// Utility methods
String str = "123";
int parsed = Integer.parseInt(str); // String to int
String converted = Integer.toString(456); // int to String
```

## Best Practices

1. **Use POJOs** for standardizing data across your application
2. **Prefer Enums over constants** for type safety and readability
3. **Use Bill Pugh or Enum Singleton** for singleton pattern
4. **Make defensive copies** in immutable classes for collections
5. **Use final keyword** to prevent unintended inheritance
6. **Leverage wrapper classes** for primitive-object conversion and collections
